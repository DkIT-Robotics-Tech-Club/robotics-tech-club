# Project Lattice - Development Roadmap

## 1. Overview

Project Lattice is planned as an eight month engineering project running from **September through April**.

Development will cover the acoustic sensing system, computer vision system, supporting electronics and software, followed by integration and testing.

The roadmap is designed around the academic year and takes into account the availability of different year groups. In particular, third and fourth year students may begin industrial placement during the second semester.

The project therefore aims to establish strong technical foundations and documentation during Semester 1 so that development can continue during Semester 2 with a smaller core team.

The roadmap is a working plan rather than a fixed schedule. Specific tasks may change as the project develops.

## 2. Phase 1 - Project Setup

**September**

The first phase establishes the foundations of the project.

### Objectives

* Finalise project requirements.
* Review the proposed system architecture.
* Identify suitable hardware.
* Set up development environments.
* Establish repository structure.
* Define initial testing methods.
* Begin technical research.
* Assign members to technical areas.

### Expected outcomes

* Agreed system architecture.
* Initial hardware list.
* Development environment established.
* Initial experiments planned.
* Initial responsibilities assigned.

## 3. Phase 2 - Core Subsystem Development

**September - November**

Development of the main acoustic and computer vision subsystems.

### Acoustic system

* Test individual microphones.
* Develop the microphone array.
* Investigate signal acquisition.
* Develop basic signal conditioning.
* Record acoustic data.
* Begin signal-processing experiments.
* Investigate suitable TDOA methods.

### Computer vision system

* Select and integrate a camera.
* Establish image capture.
* Investigate suitable computer vision approaches.
* Begin object detection experiments.
* Begin basic object tracking.

### Expected outcomes

* Working microphone hardware.
* Reliable acoustic data acquisition.
* Working camera subsystem.
* Initial acoustic and visual processing.
* Initial test data.

## 4. Phase 3 - Subsystem Development & Testing

**November - December**

The focus during this period is to get the main subsystems to a reliable baseline before the second semester.

### Objectives

* Improve acoustic signal processing.
* Test TDOA using controlled sound-source positions.
* Develop initial direction estimation.
* Improve object detection.
* Develop initial visual tracking.
* Establish repeatable test procedures.
* Record subsystem limitations.
* Document hardware and software configurations.

### Expected outcomes

By the end of Semester 1, the project should have:

* A documented acoustic subsystem.
* A documented computer vision subsystem.
* Initial direction-estimation results.
* Initial visual-tracking results.
* Working development code.
* Recorded test data.
* Clear instructions for continuing development.
* A list of outstanding technical tasks.

## 5. Semester 1 Handover

**December / before placement begins**

A formal project handover should take place before third and fourth year members begin industrial placement.

The purpose of the handover is to ensure that the project can continue without depending on members who are no longer available on campus.

### Handover should include

* Current system architecture.
* Hardware inventory.
* Circuit diagrams and wiring information.
* Software setup instructions.
* Repository documentation.
* Current code.
* Test procedures.
* Test results.
* Known problems.
* Current limitations.
* Recommended next steps.

Third and fourth year members can continue to provide guidance where possible, but the project should be capable of progressing with the remaining members.

## 6. Phase 4 - Integration

**January - February**

The second semester begins with the remaining team continuing development.

### Objectives

* Bring the acoustic and computer vision subsystems together.
* Establish communication between processing components.
* Define how acoustic and visual measurements will be represented.
* Investigate initial sensor-fusion approaches.
* Continue improving direction estimation.
* Continue improving visual tracking.

### Expected outcomes

* Integrated subsystem prototypes.
* Initial acoustic and visual data comparison.
* Initial sensor-fusion experiments.

## 7. Phase 5 - Sensor Fusion & Tracking

**February – March**

The project will investigate how information from both sensing systems can be combined.

### Objectives

* Develop an initial sensor-fusion approach.
* Compare acoustic direction estimates with visual information.
* Investigate combined target tracking.
* Test the system under controlled conditions.
* Measure system performance.
* Identify weaknesses in the integrated system.

### Expected outcomes

* Initial sensor-fusion implementation.
* Combined acoustic and visual data.
* Initial integrated tracking results.
* Performance measurements.

## 8. Phase 6 - System Integration & Refinement

**March - April**

The final development phase focuses on improving the complete demonstrator.

### Objectives

* Finalise physical sensor mounting.
* Improve hardware reliability.
* Improve software reliability.
* Conduct controlled experiments.
* Measure system performance.
* Address remaining technical issues.
* Document the final system.

### Expected outcomes

* Integrated physical demonstrator.
* Recorded test results.
* Documented system performance.
* Completed technical documentation.

## 9. Phase 7 - Final Evaluation

**April**

The final phase focuses on evaluating the project against its requirements.

### Objectives

* Run final tests.
* Compare results against the project requirements.
* Document successful and unsuccessful approaches.
* Identify system limitations.
* Record possible future improvements.
* Prepare the final project presentation.

### Expected outcomes

* Final test results.
* Completed technical documentation.
* Demonstrator ready for presentation.
* List of future development opportunities.

## 10. Team Continuity

Project Lattice should not depend on a small number of experienced members.

Third and fourth year students can provide technical guidance during Semester 1, particularly in areas requiring greater experience.

First and second year members should also be involved in the development of each subsystem so that knowledge is transferred before placement begins.

The aim is for the project to retain enough knowledge and documentation for the remaining team to continue development during Semester 2.

## 11. Development Priorities

Development will be prioritised according to the importance of each subsystem.

### Priority 1

Establish reliable sensor data acquisition.

### Priority 2

Develop usable acoustic and visual processing.

### Priority 3

Produce measurable direction and tracking results.

### Priority 4

Integrate the two sensing systems.

### Priority 5

Improve reliability and performance.

If development time becomes limited, a reliable acoustic system and functional computer vision system demonstrated independently will remain valid project outcomes. Sensor fusion and more advanced tracking can then be treated as higher-level objectives.

## 12. Risk Management

Potential challenges include:

* Poor microphone signal quality.
* Difficulty achieving reliable TDOA measurements.
* Environmental acoustic noise.
* Computer vision detection failures.
* Tracking instability.
* Processing limitations.
* Hardware availability.
* Integration problems.
* Limited development time.
* Reduced team availability during Semester 2.

The project will use staged development and documentation to reduce these risks.

## 13. Roadmap Review

The roadmap should be reviewed regularly during development.

Changes should be made when:

* Experiments produce unexpected results.
* Hardware availability changes.
* A technical approach proves unsuitable.
* Additional development time is required.
* Team availability changes.
* A subsystem reaches completion earlier than expected.

Changes to the roadmap should be documented so that the development history remains clear.
